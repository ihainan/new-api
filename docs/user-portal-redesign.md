# 用户端门户改造方案

分支 `feat/user-portal-redesign`。目标是让普通用户登录后直接看到一个可用的门户，
形态参考 ZGCAI-Coding-Plan 的 portal（领取之后的状态），去掉一切「申请 / 领取」步骤。

**管理员面板不在本次范围内，一行不改。**

---

## 1. 为什么改

现在普通用户登录后看到的是一个管理系统的删减版，不是一个「给我用的」产品：

- 侧栏两组七项：数据看板、可用模型、令牌管理、使用日志、绘图日志、任务日志、钱包管理、个人设置。
  三个日志页是按后端实现拆的（普通调用 / 绘图 / 异步任务），不是按用户想问的问题拆的。
- 命名是系统视角：「令牌管理」「钱包管理」。用户想的是「我的密钥」「我用了多少」。
- 数据看板混了系统公告、服务可用性、常见问答、API 信息、用户消耗排行——
  其中「用户消耗排行」是横向比较别人，属于管理视角。
- 最要命的一条：**令牌页可能是空的**。发令牌只发生在建号那一刻，
  存量用户、以及 `GenerateDefaultToken` 关闭期间注册的用户，进去看到的是一张空表，
  且没有任何说明。

Coding-Plan 的门户只有四页：仪表盘、API 密钥、模型、使用记录。
它的布局组件在加载时会自动补发密钥，代码注释写得很直白：
「有席位就该有 Key，没道理让用户先申请一次」。这正是本次要搬的核心。

---

## 2. 目标形态

侧栏从两组七项收敛为**一组四项**：

| 新页面 | 路由 | 取代现有的 |
|---|---|---|
| 概览 | `/console` | 数据看板（重做内容） |
| API 密钥 | `/console/token` | 令牌管理（改名 + 自动发放 + 接入示例） |
| 模型 | `/console/model-gallery` | 可用模型（改为「我现在能调什么」视角） |
| 使用记录 | `/console/log` | 使用日志 + 绘图日志 + 任务日志三合一 |

「个人设置」保留但移出主导航，收进右上角头像菜单（那本来就是它该在的地方）。

**路由全部保持不变**，只改导航呈现与页面内容。这样已有的书签、文档链接、
管理员跳转都不会断。

### 明确不做

- **不显示余额、额度、订阅状态。** 按你的要求，Coding-Plan 那块「生效中 / 待领取 /
  剩余额度」整块不搬。Model Hub 有额度概念，但本次不在用户端呈现。
  （若日后要加，是概览页加一张卡片的量，不影响本方案其余部分。）
- **不做「申请 / 领取」交互。** 没有任何按钮让用户去申请密钥。
- **不动管理员面板**：渠道、订阅、模型管理、模型部署、兑换码、用户管理、系统设置，
  代码与导航均不修改。
- **不动钱包 / 充值页面本身**，只是从主导航移除入口（页面与路由保留可直达）。
- 不改后端计费、鉴权、relay 任何逻辑。

---

## 3. 逐页方案

### 3.1 API 密钥（最优先，因为现在是坏的）

**自动发放。** 进入密钥页时，若当前用户一个可用令牌都没有，前端调用一次
「按需补发」接口，拿到密钥后直接展示。不弹窗、不确认、不叫「申请」。

后端需要一个新的自助接口：

```
POST /api/token/self/ensure-default
```

- 仅 `UserAuth()`，作用于**调用者自己**，不接受 user_id 参数。
- 幂等：已有任何 `status=1 且未删除` 的令牌则直接返回现有的，不新建。
- 复用现成的 `model.CreateDefaultTokenForUser`，不另写一套生成逻辑。
- 忽略 `GenerateDefaultToken` 开关——该开关管的是「注册时是否自动发」，
  而这个接口表达的是「用户现在需要一个」。这一点需要评审确认是否同意。

并发下两个标签页同时打开会并发调用，靠「先查后建 + 唯一性」收敛，
返回同一把密钥而不是两把。

**接入示例。** 密钥下方给可直接复制的代码片段，按协议分标签页：

- OpenAI 兼容：`curl` 与 Python SDK，`base_url` 用 `{ServerAddress}/v1`
- Anthropic 兼容：`curl` 与 Python SDK，`base_url` 用 `{ServerAddress}`

`ServerAddress` 从 `/api/status` 取，不硬编码。

**密钥展示。** 默认掩码，点击显示明文，一键复制。重新生成需二次确认。

### 3.2 概览

只保留与「我自己」有关的内容，分两块：

**调用情况**：今日请求数、今日 Token、累计 Token。

**性能指标**：平均响应、P95 响应、缓存命中率、首字延迟、失败比例。

下方一张模型分布（按请求数），表格形式，列为模型、请求数、占比。

去掉：系统公告、服务可用性、常见问答、API 信息、用户消耗排行、当前余额、充值入口。

**数据来源全部已存在**，无需新表：

| 指标 | 来源 |
|---|---|
| 请求数、Token、模型分布 | `/api/data/self`（`quota_data`，按小时+模型预聚合） |
| 缓存命中率、首字延迟、响应耗时、失败比例 | `logs` 表的 `other` 字段 |

其中后四项现有的 `/api/log/self/stat` 粒度可能不够，需要看一眼再决定是扩展它
还是新增一个 `/api/log/self/metrics`。**这是本方案唯一可能需要新写后端聚合的地方。**

口径直接沿用 `ZGCAI-New-API-Admin/docs/monthly-report-metrics.md` 里已经定版的那套，
避免同一个指标在月报和门户里算出两个数：

- 首字延迟必须同时过滤 `is_stream=1` 且 `frt > 0`（非流式存 -1000 哨兵值）
- 失败比例分母是 `type IN (2,5)`，且应叫「上游调用失败比例」
- 客户端主动断开记为成功，不计入失败

### 3.3 模型

标题下一句话说明：「你当前可以调用的模型」。

保留现有 ModelGallery 的卡片与搜索，去掉偏目录性质的展示，
每个模型加「复制模型 ID」按钮——用户拿它去填代码。

不显示价格倍率（那是管理视角）。

### 3.4 使用记录

三个日志页合一。一个表格加筛选：时间范围、模型、结果（全部 / 只看失败）、类型
（对话 / 绘图 / 任务）。类型筛选内部映射到原来三个页面各自的数据源，对用户是一个页面。

副标题：「你的每一次调用」。

## 4. 实施顺序与影响面

1. 后端：新增 `POST /api/token/self/ensure-default`（约 40 行，含测试）
2. 后端：概览所需指标接口（先评估现有 `log/self/stat` 是否够用）
3. 前端：侧栏收敛为四项 + 个人设置移入头像菜单
4. 前端：API 密钥页（自动发放 + 接入示例）
5. 前端：概览页重做
6. 前端：使用记录三合一
7. 前端：模型页调整

**管理员侧零改动的保证方式**：`SiderBar.jsx` 里 `adminItems` 整块不动；
新增的后端路由挂在 `selfRoute` 下，与 `adminRoute` 无交集；
不修改任何 `controller/channel.go`、`user.go`、`model.go` 等管理端文件。

**回滚**：全部改动在 `feat/user-portal-redesign` 分支，生产仍在 `main`。

## 5. 需要评审确认的点

1. `ensure-default` 接口忽略 `GenerateDefaultToken` 开关是否合适？
   反方观点：管理员关掉这个开关可能正是想「不要自动发密钥」，绕过它违背意图。
   正方观点：该开关字面含义是注册时自动生成，与「用户主动进入密钥页」不是同一件事。
2. 三个日志合一后，绘图与任务日志的字段差异较大（绘图有图片、任务有进度），
   统一表格是否会丢失信息？备选方案是保留类型切换但共用一个页面框架。
3. 概览的性能指标对单个用户样本量可能很小（一天几十次调用），
   P95 之类的统计量是否有意义？备选是只显示均值并标注样本数。
4. 移除余额显示后，用户额度耗尽时将没有任何提示。是否需要保留一个
   「额度不足」的错误态提示（而非常驻的余额数字）？
